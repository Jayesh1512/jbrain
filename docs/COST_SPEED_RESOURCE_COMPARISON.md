# JBrain vs GBrain: cost, speed and resources — 2026-10-27

The comparison uses the same 13,989-page EPL corpus. GBrain 0.60.402.0 used a separate PGLite brain with 14,213/14,213 chunks embedded by `openai:text-embedding-3-large` at 1,024 dimensions, balanced vector/keyword/graph retrieval, and no Voyage reranker key. JBrain used the running Rust/SQLite daemon, its local `/v1/search` and `/v1/query` retrieval paths, and `gpt-6-luna` only for the separately sampled `/v1/ask` answer path. These measurements describe this installation and corpus, not universal properties of either project.

| Measure | JBrain | GBrain with vectors |
| --- | ---: | ---: |
| Complete source-page evidence@5, familiar / hard | `/v1/query`: 66/66 / 21/36 | `search`: 58/66 / 25/36; `query`: 58/66 / 23/36 |
| Warm retrieval p50, search | 17–20 ms | 0.98–1.49 s |
| Warm retrieval p50, question query | 21–30 ms | 0.45–0.49 s |
| Warm retrieval p95, search | 29–37 ms | 1.80–6.13 s |
| Warm retrieval p95, question query | 72–84 ms | 1.00–3.40 s |
| Warm resident RSS | ~14–15 MiB | ~372–507 MiB sampled; 459–498 MiB after warmup |
| Local CPU time, one 80-request run | 0.61 CPU-seconds | 42.13 CPU-seconds |
| Corpus-specific storage | 369 MiB for canonical data, operations and derived SQLite index | 1,082 MiB PGLite database plus 58 MiB source Markdown |
| Retrieval API fee at 1,000 questions/day | $0 | About $0.002/day for query embeddings; about $0.06 per 30 days |
| One-time corpus indexing API fee | $0; deterministic import | Exact billed amount unavailable; complete embedding pass finished under a $2 cap |

The latency rows are three 40-question runs, each with 20 familiar and 20 hard answerable questions selected with seed 42. The same 40 questions were sent to both systems, with three warmup questions before timing. Both processes stayed resident; JBrain used local HTTP and GBrain used MCP stdio. Each run issued one `search` and one question-oriented `query` per system per question, sequentially, with a ten-result cap and the EPL source scope. Thus the CPU row is the combined 80-request workload, not CPU per answer. The final run's median/peak RSS was 14.0/15.0 MiB for JBrain and 372.0/506.9 MiB for GBrain. Network latency to OpenAI and local database work are both present in GBrain's vector-backed wall time; JBrain's retrieval made no provider call. The transports differ slightly, and no simultaneous-load latency claim follows from this sequential sample. Machine-readable timings are `.jbrain/gbrain-comparison/runtime-benchmark.json`; [the harness](../scripts/benchmark_runtime.py) can rerun it.

The retrieval fee uses the [matched 120-question GBrain trace](GBRAIN_COMPARISON.md): 117 query-embedding calls consumed 1,843 input tokens across 120 `query` requests. At OpenAI's current [`text-embedding-3-large` rate of $0.13/M tokens](https://developers.openai.com/api/docs/models/text-embedding-3-large), the observed mix projects to $0.001997 per 1,000 questions. GBrain's own per-request estimates rounded to about $0.000239 across the 120 calls. A different question mix, additional retrieval calls per answer, re-embedding after edits or provider pricing changes will alter this figure. JBrain's local retrieval has no model-token fee, though the host still costs compute and storage.

**Answer generation is a separate cost.** GBrain's measured `search`/`query` surfaces return evidence; they did not generate final answers. The current JBrain `/v1/ask` uses `gpt-6-luna` for generation and verification. In a two-question diagnostic sample, a simple question took 53 seconds, made six model-call attempts, ended `needs_verification`, and had a **known** $0.00125 subtotal from five usage receipts. A compound question answered in 114 seconds with 11 metered calls costing about $0.00596. The first case has one call without a usage receipt, so its exact cost is unknown. Two questions cannot predict a 1,000/day average or establish answer accuracy. The bill for a GBrain-based answer agent depends on whichever model, evidence payload and workflow it uses; no comparable final-answer path was run. OpenAI currently lists standard short-context [`gpt-6-luna` at $0.10/M input and $0.50/M output tokens](https://developers.openai.com/api/docs/models/gpt-6-luna), with separate cached-read and cache-write rates. Diagnostic receipts are `.jbrain/gbrain-comparison/luna-answer-cost-sample.json`.

The absent Voyage reranker would add expense and latency. Voyage currently lists [`rerank-3-lite` at $0.02/M processed tokens](https://docs.voyageai.com/docs/pricing) after its free-token allowance. An illustrative 25 candidates of 500–1,400 tokens per question would cost roughly $0.25–$0.70/day at 1,000 questions/day once free credits are exhausted, excluding query tokens. The actual candidate count and lengths were not recorded, so this is a scenario, not a bill or a measured accuracy gain. GBrain's balanced mode reports the reranker enabled but unready without `VOYAGE_API_KEY`.

For this corpus, JBrain is markedly lighter in local RAM, CPU and disk and faster at retrieval, while GBrain's semantic search recovers more of the hard questions that JBrain's current planner misses. Across all 102 answerable retrieval questions, JBrain `/v1/query` found 87 complete top-five page sets and GBrain vector `search` found 83. Both miss important hard categories, and those page counts do not measure final-answer correctness. JBrain's storage service has separately passed a 1/4/16-client write test; this comparison did not load-test concurrent retrieval or writes for either system. [GBrain's engine guide](https://github.com/garrytan/gbrain/blob/master/docs/ENGINES.md) describes PGLite as a single-process engine, so independent agents need to share its serving process or use its Postgres engine; this isolated test did not remove that operational constraint.
